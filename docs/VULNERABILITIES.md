# BWA Dojo Vulnerabilities

This document provides more technical information about the vulnerabilities intentionally implemented in BWA Dojo.

The vulnerabilities are part of the normal application flows rather than isolated challenge pages. They affect authentication, user profiles, products, comments, orders, and administrative functionality.

The examples below are intended only for BWA Dojo running in a local or isolated lab environment.

---

## VULN-01 — Insecure Direct Object Reference (IDOR)

### Description

The order detail endpoint requires authentication but does not verify that the requested order belongs to the authenticated user.

The vulnerability is located in the order details flow.

### Affected Endpoint

```http
POST /api/orders/show
```

### Why It Is Vulnerable

The backend accepts an `order_id` and retrieves the corresponding order, but no ownership check is performed before returning it.

This means that authentication is required, but authorization at object level is missing.

### Exploitation Methodology

1. Log in with a normal user account.
2. Open one of the orders belonging to that account.
3. Capture the request sent to:

```http
POST /api/orders/show
```

4. Observe the submitted `order_id`.
5. Replace it with the ID of an order belonging to another user.
6. Send the modified request using the same authenticated session.

### Expected Result

If the referenced order exists, the API returns the other user's order details even though the authenticated account does not own that order.

### Reference

- CWE-639 — Authorization Bypass Through User-Controlled Key

## VULN-02 — Broken Function Level Authorization (BFLA)

### Description

The administrative order endpoint requires authentication but does not correctly restrict the function to administrators.

### Affected Endpoint

```http
GET /api/orders/admin
```

### Why It Is Vulnerable

The endpoint verifies that a valid authenticated user exists, but the administrator role check is intentionally missing.

A standard user can therefore access an administrative API function.

### Exploitation Methodology

1. Log in using a normal non-admin account.
2. Obtain the JWT generated by the application.
3. Confirm that the token works with a normal user endpoint such as:

```http
GET /api/orders/me
```

4. Using the same token, send a request to:

```http
GET /api/orders/admin
```

5. Do not change the authentication context.

### Expected Result

The API returns `200 OK` together with the administrative order dataset even though the token belongs to a standard user.

Sending the same request without authentication should instead return `401 Unauthorized`.

### Reference

- CWE-862 — Missing Authorization

## VULN-03 — User Enumeration

### Description

The login endpoint reveals whether an email address exists by returning different responses for different authentication failures.

### Affected Endpoint

```http
POST /api/auth/login
```

### Why It Is Vulnerable

The backend handles these two situations differently:

- existing email with incorrect password
- non-existing email

The HTTP status code and response message are different.

### Exploitation Methodology

Send a login request using an existing email address but an incorrect password.

Example:

```json
{
  "email": "existing@example.com",
  "password": "wrong-password"
}
```

Then repeat the request using an email address that does not exist:

```json
{
  "email": "not-existing@example.com",
  "password": "wrong-password"
}
```

Compare the responses.

### Expected Result

An existing account with a wrong password returns a response similar to:

```text
401 Unauthorized
Wrong password.
```

A non-existing account returns:

```text
404 Not Found
Email not found.
```

The difference allows an attacker to determine whether an account exists.

### Reference

- CWE-204 — Observable Response Discrepancy

---

## VULN-04 — Login Brute Force

### Description

The authentication endpoint intentionally does not apply effective rate limiting, progressive delays, or temporary account lockout.

### Affected Endpoint

```http
POST /api/auth/login
```

### Why It Is Vulnerable

Repeated authentication attempts are accepted without limiting the frequency of requests.

### Exploitation Methodology

1. Identify a valid account.
2. Capture a normal login request.
3. Send the request to a tool such as Burp Intruder.
4. Mark only the password value as the payload position.
5. Load a small password wordlist.
6. Start the attack.
7. Compare response codes and response bodies.

### Expected Result

Repeated login attempts continue to be accepted.

When the correct password is eventually submitted, the server returns a successful authentication response without the previous attempts having triggered a lockout or significant delay.

### Reference

- CWE-307 — Improper Restriction of Excessive Authentication Attempts

---

## VULN-05 — Mass Assignment Leading to Privilege Escalation

### Description

The profile update functionality accepts additional properties that should not be controlled by a normal user.

Sensitive model attributes such as `role` are assignable.

### Affected Endpoint

```http
PUT /api/profile
```

### Why It Is Vulnerable

The backend applies user-controlled request data to the user model without sufficiently restricting which fields may be modified.

### Exploitation Methodology

1. Log in using a normal user account.
2. Send a normal profile update.

For example:

```json
{
  "username": "testuser"
}
```

3. Confirm that the account still has the `user` role.
4. Repeat the profile update while adding the sensitive `role` property:

```json
{
  "username": "testuser",
  "role": "admin"
}
```

5. Send the modified request.

### Expected Result

The request returns successfully and the user object now contains:

```json
{
  "role": "admin"
}
```

Administrative functionality becomes available to the account.

### Reference

- CWE-915 — Improperly Controlled Modification of Dynamically-Determined Object Attributes

---

## VULN-06 — Stored Cross-Site Scripting (XSS)

### Description

Product comments are stored by the backend and rendered by the frontend as HTML without sanitisation.

### Affected Area

Product comments and reviews.

### Why It Is Vulnerable

The comment content is stored normally, but the frontend renders it using `dangerouslySetInnerHTML`.

User-controlled content therefore becomes executable HTML.

### Exploitation Methodology

1. Log in with a normal account.
2. Open a product page.
3. Submit a comment containing an HTML/JavaScript payload.

For example:

```html
<img src=x onerror=alert('XSS')>
```

4. Submit the comment.
5. Refresh the product page.

### Expected Result

The JavaScript executes when the comment is displayed.

Because the payload is stored in the database, it executes again when the page is loaded later.

This confirms that the issue is Stored XSS rather than Reflected XSS.

### Reference

- CWE-79 — Improper Neutralization of Input During Web Page Generation

---

## VULN-07 — SQL Injection

### Description

The product search functionality inserts user-controlled input directly into a raw SQL condition.

### Affected Endpoint

```http
GET /api/products?search=...
```

### Why It Is Vulnerable

The search value is concatenated into a raw SQL expression instead of being safely parameterised.

### Exploitation Methodology

1. Open the product catalog.
2. Perform a search for a string that does not match any product.
3. Confirm that no products are returned.
4. Replace the search value with:

```text
No_match' OR 1=1--
```

5. Submit the search again.

### Expected Result

Products are returned even though the initial search term does not correspond to a product.

This demonstrates that the supplied input modified the SQL query logic.

The vulnerability can also be analysed with tools such as Burp Suite and sqlmap inside the lab environment.

### Reference

- CWE-89 — Improper Neutralization of Special Elements used in an SQL Command

---

## VULN-08 — HTTP Parameter Pollution (HPP)

### Description

The order status update functionality validates a status value from the request body but later allows the final value to be overridden by a query-string parameter.

### Affected Endpoint

```http
PATCH /api/orders/{id}/status
```

### Why It Is Vulnerable

The value that passes validation is not necessarily the value eventually used by the application.

A `status` value provided in the query string can override the validated body value.

### Exploitation Methodology

1. Authenticate as a normal non-admin user.
2. Capture an order status update request.
3. Confirm that attempting to set a restricted status normally results in:

```text
403 Forbidden
```

4. Send the request to Burp Repeater.
5. Keep a permitted value in the request body.
6. Add the following query parameter to the request URL:

```text
?status=completed
```

For example:

```http
PATCH /api/orders/1/status?status=completed
```

7. Send the modified request with the same non-admin token.

### Expected Result

The response returns `200 OK` and the order status changes to `completed`.

The query-string value has therefore overridden the value used during the intended validation path.

### Reference

- CWE-235 — Improper Handling of Extra Parameters

## VULN-09 — Security Misconfiguration

### Description

The API intentionally contains multiple configuration weaknesses.

The main examples are:

- permissive CORS configuration
- detailed internal error responses

### Affected Areas

- API CORS configuration
- global API exception handling

### Permissive CORS

The API accepts requests from arbitrary origins.

#### Validation

Send a request such as:

```http
GET /api/products
Origin: https://example.com
```

### Expected Result

The response includes a permissive CORS header such as:

```http
Access-Control-Allow-Origin: *
```

### Internal Error Disclosure

Application errors expose internal technical information.

#### Validation

Send a malformed product search request such as:

```http
GET /api/products?search='
```

### Expected Result

The API returns a `500 Internal Server Error` containing information such as:

- exception type
- exception message
- internal file path
- line number
- database or SQL error details

### Reference

- CWE-209 — Generation of Error Message Containing Sensitive Information

## VULN-10 — Host Header Injection

### Description

Some administrative endpoints make an authorization decision based on the client-controlled HTTP `Host` header.

### Affected Areas

The vulnerable logic affects administrative functionality including:

- user management
- product management
- comment moderation

### Why It Is Vulnerable

The application checks whether the request host is `localhost` instead of relying only on proper role-based authorization.

The Host header is supplied by the client and can therefore be manipulated.

### Exploitation Methodology

1. Authenticate as a normal non-admin user.
2. Send an administrative request such as:

```http
GET /api/admin/users
```

3. Use the normal backend host:

```http
Host: 127.0.0.1:8000
```

4. Confirm that the request is rejected.
5. Send the request to Burp Repeater.
6. Change only the Host header to:

```http
Host: localhost:8000
```

7. Keep the same non-admin JWT and the same endpoint.
8. Send the request again.

### Expected Result

The response changes from an authorization failure to:

```text
200 OK
```

and administrative data becomes accessible.

The same technique can also be applied while intercepting the requests generated by the administrative interface.

### Reference

- CWE-807 — Reliance on Untrusted Inputs in a Security Decision

## Validation

The vulnerabilities in BWA Dojo were manually tested in the running application after implementation.

The validation was performed in a controlled local environment using a combination of manual testing and security tools, including:

- Burp Suite Professional
- OWASP ZAP
- Nikto
- sqlmap
- Metasploit Framework

Manual testing was important because several vulnerabilities depend on application state, authorization logic, or workflow manipulation and were not reliably identified by automated scanners.

The purpose of BWA Dojo is therefore not only to provide vulnerabilities that scanners can detect, but also to provide scenarios that require manual analysis and understanding of application behaviour.

---

## Responsible Use

BWA Dojo is intentionally vulnerable.

Only use these techniques against BWA Dojo or systems where you have explicit permission to perform security testing.

Do not expose the application directly to the public Internet and do not use real credentials or production data.
